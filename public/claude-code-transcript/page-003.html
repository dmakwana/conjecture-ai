# Cloudflare Workers Static Assets `_headers` Support

Yes, Cloudflare Workers Static Assets fully supports a `_headers` file for customizing response headers.

## File Placement

The `_headers` file should be placed in your static assets directory. If using a framework with a `public/` or `static/` folder, place it there since these directories are copied to the final output during the build process.

## Syntax

Rules are defined in multi-line blocks with a URL pattern followed by indented header pairs:

```
[url]
  [name]: [value]
```

## Limits

- Maximum 100 header rules per file
- 2,000 character limit per line (including spacing, header name, and value)

## Example: Custom Header on All Paths

```txt
/*
  X-Custom-Header: my-value
```

This applies the custom header to every incoming URL. The documentation notes that "Headers defined in the `_headers` file override what Cloudflare ordinarily sends," though custom headers from `_headers` don't apply to responses generated by Worker code itself—only to static asset responses.

What I added

Four layers, in descending order of what they're actually worth:

  1. preview_urls: false in wrangler.jsonc — preview deployments publish an extra hostname (<version>-duck-invariant.<subdomain>.workers.dev) that an Access policy scoped to the production host wouldn't cover. This was a real hole worth closing.
  2. X-Robots-Tag: noindex, nofollow, noarchive, nosnippet on every response. Assets get it from public/_headers; Worker responses need it set separately in middleware, because _headers explicitly does not apply to Worker-generated responses. This one matters more than robots.txt — it also tells a crawler that already has your URL not to index it.
  3. robots.txt generated from lib/crawlers.ts — wildcard disallow plus 54 named agents.
  4. Robots meta tags (noindex, nofollow, nocache + a googlebot variant) in the layout.

The named list isn't redundant with the wildcard, which is why I built it that way: Google-Extended and Applebot-Extended aren't crawlers at all — they're AI-training opt-out control tokens that only take effect when addressed by name, and are ignored under User-agent: *. The residual risk after all of it is a link. Crawlers find URLs mainly by following them, so pasting the address into a public issue or a chat that indexes its history will do more to surface the site than these headers will prevent.

What was wrong

SET enable_external_access=false — the defence-in-depth lockdown I added so model-authored SQL can't reach a URL — is global to the DuckDB database and cannot be switched back on. Since the database was reused across loads, the lockdown applied for the first dataset poisoned every later one. So the first file in a page session worked, and everything after it hit your error, regardless of whether it came from a URL or a local file.

The dev server hot-reloads, so it should already work — hard-refresh the tab to clear the poisoned engine from the old module instance.

The fix

Re-open the database at the start of each load. That restores default settings, and unlike terminating the worker it doesn't recompile the 34 MiB wasm module, so switching datasets stays fast. Re-opening invalidates open connections, so page.tsx now releases the previous one before loading and reconnects after.

The important detail: the lockdown is re-applied on every load, not just the first. Otherwise the fix would have quietly traded your bug for a worse one — the second dataset evaluated with external access left on. There's a test asserting a remote read still fails after the second load specifically.

Why my tests missed it

The integration test only ever loaded one file. Testing that the lockdown works is not the same as testing that the app still works afterwards, and I only wrote the first half. test/reload.test.ts now covers a second and third load, that the lockdown re-applies each time, and that no rows of the previous dataset survive into the next.
